Collaboration on GitHub is highly concentrated. Of 56,519 users, almost all have only a handful of collaborators, while a few hubs and bridges hold the network together. I measured and visualized the network, found its tightest community (a 14-person clique), identified its most prolific collaborator, and built a recommender that suggests which developers should work together next.

Problem

Who drives collaboration in an open-source community, where do tight-knit groups form, and which developers who haven't worked together yet probably should? A list of repositories and contributors can't answer that. Modeling the data as a network can.

Data

  • Nodes: 56,519 GitHub users.
  • Edges: 72,900 links. Two users are linked if they contributed to the same repository.
  • Node attribute: 'grouping', the user's group.
  • Betweenness, cliques and recommendations were computed on a subsample of about 60 users, because those algorithms are slow on the full graph.

2. Visualizing the structure

A plot of 56,000 nodes is unreadable, so I drew the largest connected component and ordered nodes by a meaningful attribute.

largest_ccs = sorted(nx.connected_components(G), key=lambda x: len(x))[-1]
h = matrix(G.subgraph(largest_ccs), group_by='grouping')

for n, d in G.nodes(data=True):
    G.nodes[n]['degree'] = nx.degree(G, n)
a = arc(G, sort_by='degree')
c = circos(G, sort_by='degree', group_by='grouping', node_color_by='grouping')

3. Finding communities with cliques

A maximal clique is a group of users who have all worked with each other and can't be extended by another user. It is a natural seed for a community.

{{ fig('clique-count.png', 'Code output: 19 maximal cliques', '19 maximal cliques in the subsample.') }} 
largest_clique = sorted(nx.find_cliques(G), key=lambda x: len(x))[-1]
G_lc = G.subgraph(largest_clique)
c = circos(G_lc)
{{ fig('largest-clique-circos.png', 'Circos plot of the 14-user clique', 'Largest clique: 14 users. Every member has collaborated with all 13 others, 91 links in total.') }}

I then expanded the clique by one hop, adding every collaborator of its members, and sorted the result by degree centrality.

5. Recommending new collaborations

The recommender uses open triangles. If A has worked with both B and C, but B and C haven't worked together, they share a collaborator and are good candidates. The more collaborators a pair shares, the stronger the recommendation.

recommended = defaultdict(int)
for n, d in G.nodes(data=True):
    for n1, n2 in combinations(list(G.neighbors(n)), 2):
        if not G.has_edge(n1, n2):
            recommended[(n1, n2)] += 1

all_counts = sorted(recommended.values())
top10_pairs = [pair for pair, count in recommended.items() if count > all_counts[-10]]
{{ fig('recommendations.png', 'Code output: recommended pairs', 'Recommended pairs: (u2022, u4159) and (u655, u2022). u2022 appears in both.') }}

Only two pairs came back instead of ten. Many pairs tie with the 10th-highest count, and the strict > comparison drops all of them. The two pairs returned are the ones strictly above the cutoff, the strongest recommendations.

Recommendations

  1. Engage the hubs and bridges first. Reaching u741 and the four high-betweenness users spreads information fastest and keeps separate groups linked.
  2. Protect the clique's outside links. The 14-person group reaches the rest of the network through one or two members. If they leave, the group becomes isolated.
  3. Make the introductions. Pair u2022 with u4159 and with u655. Each pair already shares collaborators.
  4. Don't rely on the grouping label. It barely varies in this sample, so communities should be found from the links.

Challenges and what I'd improve

  • API changes. connected_components returns sets of nodes, not graphs, so it needs G.subgraph(...). G.node was removed in NetworkX 2.4, so I used G.nodes[n]. find_cliques returns a generator, so I counted it with len(list(...)).
  • Editable subgraphs. G.subgraph() returns a read-only view. Expanding the clique needed .copy().
  • Duplicate pairs. The recommender can count the same two users as both (A, B) and (B, A). I'd store tuple(sorted((n1, n2))), and use Counter.most_common(10) to always return exactly ten.
  • Subsample. Betweenness, cliques and recommendations ran on about 60 users. Next, I'd rebuild the project on a public GitHub dataset, add Louvain community detection, and score the recommender by hiding 10% of links and measuring how many it recovers.
